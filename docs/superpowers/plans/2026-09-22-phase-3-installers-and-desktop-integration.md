# Phase 3: Installers + Desktop Integration (v0.2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Spec-level plan**: each task gives interfaces, behaviour, hostile-input requirements and acceptance tests; the implementer writes code test-first. Phases 1-2 showed plan-supplied code is the weak point — this plan supplies requirements, not code.

**Goal:** `runtime install setup.exe|installer.msi` runs the installer (sandboxed), finds what it installed, and makes the result appear as a normal Linux application — a `.desktop` entry with an icon, launchable from the app grid, uninstallable with `runtime uninstall`.

**Architecture:** New crate `installer` (pipeline: detect -> analyze -> sandbox -> run -> snapshot-diff -> discover -> rank) depending on `rt_core`, `pe`, and the new `Sandbox` seam in `rt_core::backend::Launcher`. New crate `desktop` (`.desktop` generation, icon extraction/conversion, MIME/file-association, calling `update-desktop-database`/`update-mime-database`). `cli` gains `install` support for `.msi`, and `uninstall`.

**Tech Stack:** Rust 2024 (MSRV 1.88), `bwrap` (external, already present) for the installer sandbox (`D7`: minimal profile now, full Phase 5 later), `lnk` crate (MIT, parses `.lnk` Shell Links) or a hand-rolled `[MS-SHLLINK]` reader if `lnk`'s API doesn't fit — decide in Task 3 and document why, `png`/`ico` handling (prefer a small vetted crate for ICO parsing, e.g. `ico`, over hand-rolling BMP/PNG-in-ICO edge cases), Wine's own `msiexec` and the installer's own `.exe` (both invoked as *installers*, sandboxed, never as the final Windows API).

**Spec:** Master prompt §22-24, §27, §46; roadmap Phase 3 (`docs/superpowers/plans/2026-09-21-runtime-master-roadmap.md`). Builds on Phase 2 (`docs/superpowers/plans/2026-09-21-phase-2-environments-and-wine-backend.md`), whose `CompatBackend`/`Launcher`/`AppEnv`/`Store`/`install` this phase extends, not replaces.

## Global Constraints

- Everything from the installer file, the sandboxed installer process, the registry snapshot, and file names discovered on disk is UNTRUSTED. No panics; bounded work; failures reported, never swallowed (Phase 1/2 standard carries over verbatim).
- **Installers are sandboxed from day one (§28, roadmap D7).** No unsandboxed installer execution ships in this phase. The sandbox is intentionally minimal (this is not Phase 5): no real `$HOME`, `Downloads` read-only by default, network on by default with an opt-out, no new devices/USB. Document the limits as honestly as Phase 2's `docs/SECURITY.md` does.
- Every untrusted string printed goes through the shared sanitiser (`rt_core::is_format` / `cli::safe`, extended in Phase 2 Task 4 — reuse it, do not fork a third copy).
- No shell interpolation anywhere. `Command` with argument vectors only.
- Default behaviour shows the installer's own UI (master prompt §22: "default = show installer GUI"); silent flags are opt-in per the family-flag matrix (Task 2), never assumed.
- Never require root for a normal install. `bwrap` runs unprivileged (it is setuid-root itself on most distros, but the *runtime* process does not need root).
- Manual override always exists: `runtime install --exe "C:\Program Files\X\x.exe"` when discovery guesses wrong (master prompt §22 risk mitigation) — build this from Task 1 alongside automatic discovery, not as an afterthought.
- fmt/clippy `-D warnings`/tests green before every commit; every new security guard gets a test that fails when the guard is removed (mutation-checked, named failing test pasted in the implementer's report).
- Nothing in this phase requires network access from the runtime itself (no downloading dependencies — that is Phase 4). If a task's tests need a real NSIS/MSI fixture, build it locally with `makensis`/`wixl` (Task 0), never fetch one from the internet.

## Spike findings (this machine; why the design looks like this)

| Finding | Consequence |
|---|---|
| `nsis` (`makensis`) and `msitools` (`wixl`) are both in the Ubuntu repos but not installed; both build REAL `.exe`/`.msi` files locally, no network, no Windows | Task 0 fixtures use them; no Inno Setup compiler exists for Linux, so Inno support is validated against a hand-built synthetic fixture (Phase 1 style) for detection, and against a real Inno installer only if the user supplies one |
| `python3 -m msilib` was removed (deprecated Py3.11, gone in 3.13) | Cannot use it to build/inspect `.msi` fixtures in test tooling; use `wixl`-built `.msi` + Wine's own `msiexec` for execution, and parse MSI structure (an OLE2/CFB compound file) with a Rust crate or the minimal reader Task 4 needs |
| Wine's registry files (`system.reg`/`user.reg`) are a **plain-text** format (`WINE REGISTRY Version 2`, `[Key\\Path] timestamp` / `"Name"="Value"` / `#time=...`), not the real Windows binary hive format | Task 2's registry-diff parser is a small text parser, not a binary regf reader — far simpler than the master prompt implies for a Wine backend |
| `desktop-file-validate`, `update-desktop-database`, `update-mime-database`, `xdg-icon-resource` are all installed | Task 3 shells out to these for validation/registration instead of reimplementing `.desktop`/MIME spec compliance |
| `bwrap` is present and unprivileged-runnable (checked Phase 0) | Task 5's installer sandbox is real bubblewrap namespaces, not a stub |
| `lnk`/`parselnk`/`mslnk`/`lnk-core` crates exist on crates.io | Task 3 picks one (or documents why not) instead of writing a `[MS-SHLLINK]` parser from scratch — but audit it the way Phase 1 audited `pelite`: assume it may panic on hostile bytes, wrap accordingly |

**Goal:** produce real, locally-built `.msi` and NSIS `.exe` installers for every later task's tests, with no network fetch and no Windows.

- [ ] `tools/fixtures/hello.wxs`: a minimal WiX source installing `tests/fixtures/build/hello64.exe` (from Phase 1) to `[ProgramFilesFolder]RuntimeFixture\hello64.exe`, a Start Menu shortcut, and a registered `Uninstall` entry with `ProductName` "Runtime Fixture MSI", a fixed `UpgradeCode`/`ProductCode` GUID (documented, not random, so tests are deterministic). - [ ] `tools/fixtures/hello.nsi`: a minimal NSIS script installing the same `hello64.exe` to `$PROGRAMFILES64\RuntimeFixtureNsis\`, a Start Menu shortcut, an `Uninstall` registry key, and a silent-install path reachable with `/S`. - [ ] Verify both fixtures with `wine msiexec /i hello.msi /qn` and `wine hello-nsis.exe /S` in a scratch prefix; confirm `hello64.exe` lands and the Start Menu `.lnk` exists; confirm the SAME artifacts are produced by a normal (non-silent) run for the default-UI tests, by watching a screenshot is NOT required — assert on files/registry only, and time out any interactive dialog rather than blocking (installers built here must not pop a real dialog when run silently; the non-silent path is tested with a bounded timeout and treated as "did not finish in time" being an acceptable, asserted outcome, never a hang).

## Task 1: `InstallerFamily` and the silent-flag matrix

**Interfaces:** `InstallerFamily { Inno, Nsis, InstallShield, WixBurn, Msi, Unknown }` (from `pe::InstallerKind` plus MSI-magic detection, already in `pe::detect`). `SilentFlags { args: Vec<OsString>, note: &'static str }` per family (Inno: `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP-`; NSIS: `/S`; InstallShield: `/s` — documented as unreliable, many InstallShield installers need a generated `.iss` response file, note this limit; WiX Burn: `/quiet /norestart`; MSI: handled separately via `msiexec /i <path> /qn /norestart`, not passed to the exe itself). `fn plan(kind: InstallerFamily, silent: bool) -> RunPlan { program: Program::Exe | Program::MsiExec, args }`. **No flags are ever applied unless the caller opts in** (`--silent`/default-GUI decided in Task 6).

**Tests:** table test over every family x silent/not; MSI never returns `Program::Exe`; unknown family + silent requested -> explicit error (never guesses a flag), tested.

## Task 2: Wine `.reg` text parser and snapshot diff

**Interfaces:** `WineReg::parse(bytes: &[u8]) -> Result<WineReg, RegError>` for the `WINE REGISTRY Version 2` text format (keys `[Path] timestamp`, values `"Name"="string"` / `"Name"=dword:hex` / `@="default"`, `#time=` lines ignored, hex-escaped strings `\"`/`\\`/`\r`/`\n` per Wine's own escaping). Bounded (line length cap, key-path depth cap, total size cap matching the existing 4 GiB whole-file ceiling), no panics on truncated/malformed lines (skip the line, count it, never abort the whole parse — same "report don't swallow" standard, one aggregate warning for skipped lines). `Snapshot::capture(env: &AppEnv) -> Snapshot` (drive_c file listing — reuse/extend `doctor`'s bounded `Listing` type from Phase 2 — plus parsed `system.reg`+`user.reg`). `Snapshot::diff(before, after) -> InstallDiff { new_files: Vec<WinPath>, new_registry_keys: Vec<(Hive, String)>, uninstall_entries: Vec<UninstallEntry{display_name, uninstall_string, icon_path}> }`. `UninstallEntry` comes from `HKLM\...\Uninstall\*` / `HKCU\...\Uninstall\*` subkeys present after but not before.

**Security standard:** the registry text and every file name are attacker-controlled (a hostile installer writes them). Every string that reaches `InstallDiff` is later escaped by `desktop`/`cli`'s sanitiser before display — say so in doc comments. Bounded listing (reuse Phase 2's cap-and-report-truncation pattern, do not silently miss entries).

**Tests:** parser table (valid keys/values, escaped quotes, dword, default value `@=`, malformed lines skipped with a warning, truncated file, 20 000-line synthetic file for bound-checking); diff correctness on two hand-built Wine reg snapshots (added key, added value, removed key — removed is not "new", ignore it); Uninstall-entry extraction from a synthetic `user.reg`/`system.reg` pair; hostile registry values (control chars, 100 KB single value, deeply nested key path) never panic (mutation-checked cap removal test).

## Task 3: `.lnk` shortcuts, icon extraction, candidate ranking

**Interfaces:** `ShellLink::parse(bytes: &[u8]) -> Result<ShellLink, LnkError>` wrapping the chosen crate (or a hand-rolled minimal `[MS-SHLLINK]` reader if the crate's error handling on hostile input is not acceptable — spike this first: fuzz the candidate crate for 10k iterations the way Phase 1 fuzzed `pelite`, and if it panics, either wrap in `catch_unwind` at the one call site with a documented reason, OR write the minimal reader yourself; do NOT silently trust it). Exposes at least `relative_path: Option<WinPath>`, `icon_location: Option<(WinPath, i32)>` (path + icon index), `working_dir: Option<WinPath>`. `rt_desktop::icon::extract_icon_png(pe_bytes: &[u8], sizes: &[u32]) -> Result<Vec<(u32, Vec<u8>)>, IconError>`: reads the PE's icon-group resource (via `pe` crate's existing resource directory walk — extend `pe` minimally if a needed accessor is missing, in its own reviewed commit), picks the best match per requested hicolor size (16/32/48/128/256), decodes the embedded ICO/PNG-in-ICO entry, re-encodes as PNG. Bounded: reject icon dimensions absurd for a 256-max hicolor set, reject decompression bombs in PNG-in-ICO the same way Phase 1's `unzip`/`version.rs` bounded their inputs (a small size cap on the decoded bitmap, e.g. 1024x1024x4 bytes). `discover::rank(diff: &InstallDiff, shortcuts: &[ShellLink]) -> Vec<Candidate{path, name, icon: Option<...>, score}>`: score by (has a matching Start Menu `.lnk`) > (has an Uninstall entry naming it) > (GUI subsystem per `pe::analyze`) > (largest file), same tie-break honesty as Phase 2's install `exe` selection (ties -> ask the user, never silently pick).

**Tests:** `.lnk` parser on a real shortcut produced by Wine during Task 0's fixture verification (capture one and commit its bytes as a small binary fixture, like the mingw `.exe` fixtures — check size is small, a few hundred bytes) plus hostile/truncated/fuzzed bytes never panic; icon extraction on `tests/fixtures/build/hello64.exe`'s resources if it has any (Phase 1's `hello.rc` may need one added — coordinate: add a tiny icon resource to `tools/fixtures/hello.rc` if none exists, in a small preparatory commit with its own test) and on a crafted hostile icon resource (huge declared dimensions, truncated ICO) never panics and bounds memory; ranking table test with synthetic diffs (unambiguous winner, tie -> `NeedsManualChoice` result, never a silent guess).

## Task 4: MSI structural facts

**Interfaces:** `MsiInfo { product_name: String, product_code: String, upgrade_code: Option<String> }` read from a `.msi`'s OLE2/CFB structure and MSI string pool/tables (`_Property` table rows `ProductName`, `ProductCode`, `UpgradeCode`). Decide: hand-roll a minimal reader (CFB directory walk + the specific two MSI tables needed) bounded and hostile-input-hardened like Phase 1's PE work, OR a vetted crate if one exists with acceptable licensing/hostile-input posture — spike both before choosing, document the decision and licence in `docs/THIRD_PARTY.md`. Never attempts full MSI table-relationship parsing; explicitly out of scope beyond these three facts (say so, `STATUS_NOT_IMPLEMENTED`-style for anything else, per master prompt §51).

**Tests:** read `tests/fixtures/build/hello.msi` (Task 0) and assert the exact `ProductName`/`ProductCode` from `hello.wxs`; hostile/truncated/corrupted `.msi` bytes (bad CFB magic, truncated directory, huge declared stream sizes) never panic, bounded work, clear error — mutation-checked like every other Phase 1/2 parser.

## Task 5: Installer sandbox (`bwrap`, minimal profile)

**Interfaces:** `InstallerSandbox::wrap(cmd: Command, env: &AppEnv, opts: &SandboxOpts{allow_network: bool}) -> Command` — a PURE argv-builder (`bwrap` invocation), unit-testable without running `bwrap` (assert the exact argv for given inputs, the way Phase 2's `command()` tests asserted exact env/argv without spawning Wine). Profile: bind the app's own `prefix`/`drive_c` read-write, bind `/usr`,`/lib`,`/lib64`,`/etc/alternatives` (or whatever the discovered Wine binary needs) read-only, a private `/tmp`, no real `$HOME` (a scratch empty dir instead, consistent with Phase 2's `runtime/home`), `Downloads`/real filesystem NOT bound at all (stricter than Phase 2's Wine hardening: the installer gets nothing outside its own prefix by default), network namespace unshared by default unless `allow_network` (installers that need to phone home for a redistributable are Phase 4's problem; document that offline-only installers are the Phase 3 target), no `--dev-bind`, a fresh PID/UTS/IPC namespace, `--die-with-parent`. Wire it into the ONE existing spawn point: `Launcher::wrap` (the Phase 2 seam built exactly for this) so `installer::pipeline` reuses `Launcher`/`run_helper` rather than inventing a second spawn path. Document in `docs/SECURITY.md` exactly what this narrows and what it still does not stop (a documented-honest addition, not a new claim of "sandboxed" for the rest of the runtime).

**Tests:** argv-builder unit tests (exact bwrap args for various opts, no shell, paths escaped as argv elements not shell text); a REAL `bwrap`-executed test (not `#[ignore]`d if bwrap is fast and always present per Phase 0's spike, but gate with a availability check like Phase 2's `discover` pattern and skip loudly if `bwrap` is missing) that: the app cannot read a canary file placed in the real `$HOME`, cannot write outside its own prefix, CAN read/write inside its prefix, and (network case) cannot resolve DNS when `allow_network=false` and can when `true` (use a loopback check or `getaddrinfo` probe fixture, not a real internet call in CI — say if this needs `tools/fixtures/net.c`, a tiny probe program, built alongside the others).

## Task 6: Install pipeline (`installer::pipeline`) and CLI wiring

**Interfaces:** `install_via_installer(store, backend, launcher, path, opts: InstallerOpts{silent: bool, allow_network: bool, exe_override: Option<String>}) -> Result<InstallOutcome, InstallerError>` implementing the master-prompt §22 pipeline: detect (`pe::detect`/MSI magic) -> analyze (family, `MsiInfo` if MSI) -> create env + `backend.prepare` (Phase 2, unchanged) -> snapshot before -> run installer sandboxed via `Launcher::wrap` + `InstallerSandbox` (MSI: `wine msiexec /i <path-in-prefix> [flags]`; exe: `wine <path-in-prefix> [flags]`; the installer file itself is copied into the prefix first the same containment-safe way Phase 2's `install` copies a portable exe, never run from outside `drive_c`) -> snapshot after -> diff -> discover candidates -> on ambiguity, return `InstallOutcome::NeedsChoice(candidates)` for the CLI to ask the user (`--exe` override short-circuits this) -> write `Metadata` (extends Phase 2's schema: `installer: Option<{family, product_name, uninstall_command}>`, `schemaVersion` bump with a documented, tested migration — old metadata without the field must still `Metadata::read` successfully) -> generate desktop entry (Task 7) -> record uninstall info. `runtime uninstall <id>`: read metadata's `uninstall_command` if present, run it sandboxed the same way, THEN remove the env and desktop entry regardless of the uninstaller's exit code (report failure, do not leave a half state); apps with no recorded uninstaller fall back to plain env removal (documented as a known limit, matches roadmap). CLI: `runtime install setup.exe|installer.msi [--exe PATH] [--silent] [--network]` (network default OFF, silent default OFF matching "default = show installer GUI"); on ambiguity, print numbered candidates and exit 1 with the `--exe` hint (never a fake auto-pick); `runtime uninstall <id>`.

**Tests:** full pipeline against Task 0's real `hello.msi` and `hello-nsis.exe` via `FakeBackend` where possible for logic (id/naming/metadata/cleanup-on-failure, mirroring Phase 2 Task 6's test style exactly) and a small set of `#[ignore]`d real-Wine e2e tests (Task 8) for the actual install+desktop-entry+uninstall round trip; metadata schema migration test (old-shape JSON still reads); ambiguous-discovery path returns candidates and installs nothing; cleanup on every failure path (sandbox spawn failure, installer non-zero exit — is that even a failure? some installers exit non-zero on success with warnings: treat non-zero as `Warn`, not automatic failure, and still attempt discovery — document this explicitly and test it) leaves no half-built env.

## Task 7: `.desktop` generation, icons, MIME

**Interfaces:** `rt_desktop::entry::write(app: &AppEnv, meta: &Metadata, icon_pngs: &[(u32, Vec<u8>)]) -> Result<(), DesktopError>`: writes `~/.local/share/applications/runtime-<id>.desktop` (`Name=`, `Exec=runtime run <id>` with the id shell-escaped even though `runtime` itself never uses a shell — `.desktop` `Exec=` has its own quoting rules per the spec, handle them correctly and test hostile names with spaces/`%`/quotes), `Icon=` pointing at installed hicolor PNGs (`~/.local/share/icons/hicolor/<size>x<size>/apps/runtime-<id>.png`, via `xdg-icon-resource install --noupdate` per size, one final `xdg-icon-resource forceupdate` — or write files directly and call `update-desktop-database`+`gtk-update-icon-cache`-equivalent only if `xdg-icon-resource` proves awkward: decide and document), `Terminal=false`, `Categories=` a safe default, `StartupWMClass=` omitted (Wine window class matching is not attempted in Phase 3). Every field sourced from `Metadata`/PE resources goes through the shared sanitiser before being written (a `.desktop` file with a raw ESC or embedded `\n` in `Name=` is the same class of injection Phase 2 fixed in the CLI — do not reintroduce it here). Validate with `desktop-file-validate` after writing (shell out, treat a validation failure as a hard error, never ship an invalid file). `rt_desktop::mime`: register `.exe`/`.msi` MIME association pointing at `runtime install %f` / a right-click "Install with Runtime" (`.desktop` `MimeType=` + a second `.desktop` for the install action, or one `.desktop` with both — pick the simpler correct option and justify it), call `update-mime-database`/`update-desktop-database` afterward. `remove(app_id)` deletes the `.desktop` and icon files it created (track exactly what was written, in metadata or a manifest file, so removal never guesses a glob).

**Tests:** `.desktop` content exact-match tests for hostile names (spaces, `%`, quotes, control chars, very long names truncated per the doc's length cap) each still passing `desktop-file-validate` (a real subprocess call in the test, gated on the tool's presence like Task 5's bwrap gate); icon file placement at the right hicolor paths; MIME `.desktop` content; remove() deletes exactly the tracked files and nothing else (a canary file test, same style as Phase 2's `Store::remove` canary tests); a real end-to-end check that after `write()`, `desktop-file-validate` on the actual installed path and `grep`-style presence check in a scratch `XDG_DATA_HOME` (never the real one — every test must set `XDG_DATA_HOME`/`XDG_DATA_DIRS` to a scratch dir, the way Phase 2 tests never touched the real `~/.wine` or real `RUNTIME_DATA_DIR`).

## Execution notes (added after the phase was implemented)

The plan was spec-level; the repository is the truth. What differs from, or was added to, the plan:

**Installer sandbox (Task 5, corrected by Task 8)**

- The profile that shipped binds `/usr`, `/bin`, `/lib`, `/lib64`, `/etc/alternatives` read-only (plus `SandboxOpts::extra_ro_binds`, sourced from `CompatBackend::dll_dirs()` per Ruling 6.3, never a new `backend-wine`-specific coupling), the app's own `prefix` read-write, an empty `tmpfs` for `$HOME`, a fresh `/tmp`/`/proc`/`/dev`, a fresh PID/UTS/IPC namespace, `--new-session`, `--die-with-parent`, and the network namespace unshared unless `allow_network`. `/bin` was NOT in the plan's own text (which named `/usr,/lib,/lib64,/etc/alternatives`) and had to be added by Task 8 (see below) after real end-to-end testing found the whole sandbox silently non-functional on stock Ubuntu without it.
- The mount-order hazard the plan did not anticipate: a later `bwrap` bind wins over an earlier one at the same or a nested path, so `$HOME`'s empty `tmpfs` and the app's `prefix` bind are ordered relative to EACH OTHER at runtime (whichever is the ancestor mounts first), not a fixed argv order — otherwise a `$HOME` that happened to be the prefix itself (or an ancestor of it) would silently swallow the whole prefix. Found and fixed in Task 5's own fix round, reproduced against real `bwrap`.
- `RUNTIME_REQUIRE_BWRAP=1`/`RUNTIME_REQUIRE_DESKTOP_FILE_VALIDATE=1`: both gate the "real subprocess, not a stub" tests as a HARD failure when the tool is missing, instead of the default loud-skip-and-pass. Neither existed in the plan text; both were added by fix rounds (Task 5 finding 5, Task 7 finding 2) after reviewers found CI could go green without ever running the mandated real-tool tests, and Task 6/8 wired the corresponding CI env vars and apt packages in.

**Install pipeline (Task 6)**

- The installer file is placed inside `drive_c` (a fixed `C:\Windows\Temp\rt-installer\` staging directory) BEFORE the "before" snapshot is taken, not after: `Snapshot`/`InstallDiff` compare real on-disk paths, so placing it first means it is structurally part of the baseline and can never appear in `diff.new_files`, regardless of the on-disk casing Wine actually uses (`windows/temp/...`, lowercase) versus the WinPath text spelling (`Windows\Temp\...`) the plan's own §22 pipeline sketch implied a string-exclusion could use. An earlier version used exactly that string-exclusion, placed the installer AFTER the snapshot, and the casing mismatch meant the exclusion silently never matched — the staged installer itself could win `discover::rank` and get re-run forever as the app's own executable (Task 6 review, Critical, fixed by the reorder).
- MSI dispatch: `exe_unix` = `drive_c/windows/system32/msiexec.exe` (verified to exist in every real Wine prefix), `args = ["/i", <winpath>, ...silent_flags]` (Ruling 6.2); exe-family dispatch runs the placed installer directly. The staged installer file is deleted after a successful run (fixed in Task 6's fix round: the first version left a permanent second copy per app forever).
- CLI dispatch peeks at the file's real content (never extension) through `rt_core::read_input` — the same `metadata`-then-`O_NONBLOCK`-open, cap-checked-read discipline the rest of this project uses — not a second hand-rolled `fs::read` (Task 6's fix round: the first version's peek was a raw `fs::read`, a FIFO-swap TOCTOU the rest of the codebase already guards against elsewhere).
- A non-zero installer exit code is a warning, never a failure (documented: some installers, especially older InstallShield stubs, exit non-zero on a genuinely successful silent install); discovery still runs regardless.

**Desktop entries (Task 7)**

- Filenames are deterministic, derived only from `AppId` (`runtime-<id>.desktop`, `runtime-<id>.png` per hicolor size) — no manifest file tracking what was written, matching this codebase's existing "derive, don't store" philosophy (Ruling 7.1). `remove(id)` reconstructs every path from the id alone.
- `.desktop` `Exec=`/`Name=` escaping is a from-scratch, freedesktop-spec-correct escaper local to `rt_desktop::entry`, NOT a reuse of `crate::safe` (Ruling 7.3): that module is terminal-safety, not `.desktop`-file-safety, and is `pub(crate)` to the `cli` crate besides.
- `runtime remove` was NOT wired to `rt_desktop::entry::remove` in Task 7's first pass — only `runtime uninstall` was, despite the commit message's "install/uninstall" framing. Since this project's own e2e suite (and, presumably, most real users) calls `remove` far more than `uninstall`, this orphaned `.desktop` entries/icons pointing at a dead `runtime run <id>` for every `remove`d installer-pipeline app. Fixed in Task 7's fix round with a single shared `crate::remove_desktop_entry` helper called from both `remove.rs` and `uninstall.rs` — the exact kind of single-shared-function root-cause fix this project's own review discipline asks for.

**e2e/CI (Task 8) and the four pre-made rulings**

- Ruling (Task 6/7/8, apt packages): the plan's own text names `nsis bubblewrap msitools`; this system's actual apt split needs FOUR packages — `wixl` is separate from `msitools` on this apt (`sudo apt install msitools wixl`, per `tools/build-fixtures.sh`'s own error hint and this session's real install history). Both the `test` and `wine-e2e` CI jobs now install all four (`test` also needs `bubblewrap`/`desktop-file-utils` for its own bwrap/desktop-file-validate-gated unit tests; `wine-e2e` needs the full set to build the fixtures and run `e2e_installers.rs` for real).
- Ruling (Task 8, shared `Rig`): `crates/cli/tests/support/mod.rs` is a plain module file, not its own test binary (Cargo only turns a file directly under `tests/` into a binary target; a subdirectory is never scanned), included with a plain `mod support;` from each of `e2e_wine.rs`/`e2e_installers.rs` — no `#[path]` attribute needed, default module resolution already finds `tests/support/mod.rs` relative to the including file's own directory. Verified: `e2e_wine.rs`'s three existing tests compile and pass completely unchanged after the extraction. The shared module needs `#![allow(dead_code)]`: it is compiled once PER including test binary (each is a separate crate), and no single binary uses every method (e.g. `e2e_installers.rs` never needs the persistent-`wineserver`-survives-`remove` dance; `e2e_wine.rs` never needs the `XDG_DATA_HOME` scratch dir) — `pub` alone does not silence `dead_code` in a test-binary crate the way it would in a library crate, confirmed by actually building and reading the warnings.
- Ruling (Task 8, CI gates): the `wine-e2e` job gained `RUNTIME_REQUIRE_BWRAP=1`/`RUNTIME_REQUIRE_DESKTOP_FILE_VALIDATE=1` on its test step and `desktop-file-utils` on its apt line, matching the `test` job's own already-established convention (Tasks 6/7's fix rounds) — the plan's real e2e check explicitly wants ".desktop file exists ... and validates," which needs the real tool present and required, not optionally skipped.
- Ruling (Task 8, non-silent install, Ruling 4): the plan assumed a non-`--silent` install either times out or needs confirmation. Real testing found a THIRD outcome the plan did not anticipate: `hello.msi` (the MSI fixture) has no `<UI>` table at all, so `msiexec` has nothing to show and installs successfully regardless of `--silent` — genuinely correct behaviour, not a bug, and not usable to exercise the no-display gap. `hello-nsis.exe` (no `/S`) DOES try to show a real wizard and genuinely fails fast (~10-15s, no candidate files, never a hang) for lack of a display socket. `e2e_installers.rs`'s non-silent test uses the NSIS fixture for exactly this reason.
- **Real end-to-end testing found a Critical, previously invisible sandbox bug**, not anticipated by any prior task's review: Ubuntu's/Debian's `wine`/`wine64` commands are `update-alternatives` symlinks to `#!/bin/sh -e` wrapper scripts, not plain ELF binaries; without `/bin` in the sandbox's fixed read-only bind set, the wrapper's shebang interpreter could not be found inside the sandbox's mount namespace at all, so EVERY installer run through it failed silently (`bwrap`'s own error, `execvp /usr/bin/wine: No such file or directory`, reads exactly like "Wine is missing" and is not). This made the entire Task 6/7 installer pipeline non-functional on the exact stock Ubuntu Wine setup this project's own README/SECURITY.md tell a user to install, for every install, silent or not — invisible to every prior unit/hostile-input test because they exercise the sandbox with a trivial `/usr/bin/sh` payload, never a real Wine invocation through it. Fixed by adding `/bin` to `RO_BINDS` (`crates/installer/src/sandbox.rs`); see `docs/SECURITY.md`'s "Task 8: what real end-to-end testing found" for the full story and verification.
- **Real end-to-end testing also found an unresolved discovery/ranking gap, filed for the next review, not fixed in Task 8**: a real Wine-created Start Menu shortcut carries its target only in `LinkTargetIDList`, which `rt_installer::lnk` deliberately never parses (a documented scope limit since Task 3, itself verified against a real captured Wine `.lnk`). `discover::rank`'s tier (1) — "named by a Start Menu `.lnk`'s target" — therefore never fires against a real installer's shortcut, and for `hello-nsis.exe` (whose installer also registers a separate `uninstall.exe` in the `Uninstall` registry key) tier (2) uniquely, and wrongly, picks `uninstall.exe` as the app's own executable — confidently, not ambiguously, so `NeedsChoice` is never raised to catch it. `runtime run <id>` on such an app would silently run the uninstaller. This is a real parsing/ranking gap (teaching `rt_installer::lnk` to read `LinkTargetIDList` is a real addition to a hostile-input crate, squarely Task 3/6's scope), not something Task 8 fixes; `e2e_installers.rs`'s NSIS test uses `--exe` to sidestep it, documented inline and in `docs/SECURITY.md`. **Superseded:** Task 9 fixed the `LinkTargetIDList` gap, and the final whole-branch review corrected the cause: the registry diff was always empty (C1 below), so tier (2) never fired and the wrong pick really came from tier (3), the GUI-subsystem heuristic. Both are fixed; the NSIS e2e test now runs without `--exe`.
